## Основные архитектурные недостатки 4.0
1. **Старая монолитная база.** README прямо указывает, что `U_Ilem_4_0_base.html` является рабочей копией базы 3.2, а сервер модифицирует HTML строковыми заменами и вставляет шесть скриптов.
2. **Глобальное состояние.** Модули читают и меняют общий объект `G`, вызывают глобальные `save()`, `render()`, `toast()`, напрямую обращаются к `window`. Это создаёт скрытые зависимости и затрудняет независимое тестирование.
3. **Слабая граница UI/логики.** Модули содержат и доменные расчёты, и HTML-разметку, и обработчики карты. 5.0 должна разделить домен, приложения, UI и рендерер.
4. **Карта не является полноценной 3D-сценой.** Отчёт 4.0 говорит, что индивидуальные растения и изделия отображаются координатными маркерами поверх карты, новые постройки — маркерами; полная 3D-геометрия общей карты отсутствует. Следовательно, замена PNG в HTML не могла превратить игру в желаемую объёмную интерактивную симуляцию.
5. **Позиции заданы в процентах контейнера.** Экология и освещение рассчитывают позиции относительно прямоугольника DOM-элемента `scene`. Для 5.0 нужна независимая система координат мира и калибровка по исходной карте.
6. **Пересечения режимов размещения.** Модули вынуждены вручную отменять режимы других модулей (стройка, растения, мастерская, свет). В 5.0 должен быть единый PlacementController с активным режимом и строгой отменой/подтверждением.
7. **Одна модель состояния обслуживает все системы.** В 5.0 нужны валидируемые сущности, доменные команды и транзакции для денег/склада/задач.
8. **Сборка страницы неявная.** Сервер собирает runtime HTML на лету, в том числе заменами строк. Для 5.0 нужен прозрачный процесс сборки, единая точка входа и явная карта зависимостей.
9. **Проверки неполные.** В репозитории есть тестовые сценарии для строительства (11), экологии (10), интерьеров (11), производства (12), воды (17); отчёт заявляет эти количества. Они не запускались в текущей сессии. README не перечисляет отдельный тест освещения. Нет доказательства сквозного UI-теста, Windows запуска и браузерной визуальной проверки.
10. **Известные UI/интеграционные дефекты из переписки** — задачи/календарь, осмотры/дефекты/закупки, командный чат, выбранный объект, кнопки карты и склад — не закрываются наличием отдельных модулей и требуют отдельных сценариев приёмки.

## Что полезно сохранить как проверенные идеи
- Многоэтапные строительные проекты и раздельное утверждение закупки.
- Проверка доступности материалов/инструментов до списания ресурсов.
- Рецепты мастерской с атомарной проверкой входов.
- Индивидуальные растения с явными координатами и историей.
- Водный суточный баланс и защита от повторного тика одной даты.
- Защита несущих стен как идея, если интерьерная система будет разрешена.
- История операций/событий как часть UX.
- Тесты доменных сценариев через изолированный контекст.

## Что не переносить напрямую
- Монолитную HTML-страницу 3.2.
- Строковые замены HTML в сервере как способ собирать приложение.
- Прямые обращения модулей к глобальному `G` и глобальным функциям.
- Позиционирование мира через CSS-проценты без системы координат.
- Разрозненные режимы размещения внутри каждого модуля.
- Считать наличие тестового файла доказательством прохождения тестов.
- Считать PNG-карту готовой интерактивной 3D-сценой.

## Ключевой вывод
4.0 содержит ценные прототипы хозяйственных подсистем, но её фундамент — монолитная 2D HTML-база с DOM-маркерами. Для цели пользователя нужна новая сцена и новая архитектура. Поэтому 5.0 строится заново; из 4.0 переносятся только проверенные правила и расчёты после переписывания/тестирования.
